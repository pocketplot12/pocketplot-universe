PocketPlot · Operational Reference · v1.0

Stripe setup & CLI testing guide

Two things in one document: how to point PocketPlot at a real Stripe account (Product, Price, Webhook), and how to test the whole pipeline locally with the Stripe CLI before you ever deploy.

⏱ Time required 15–25 minutes for the first run, including account creation. After that, 5 minutes to point a fresh deploy at a new Stripe account. The CLI section takes another 10 minutes and is the part you'll come back to every time you change webhook logic.
Prerequisites PocketPlot v2 installed and running (python3 app.py). Python 3.10+. macOS, Linux, or WSL. ~50 MB free disk for the CLI.

§0Test mode vs live mode — read this first

Stripe has a toggle in the top-right of the dashboard that switches between two completely separate environments. Test mode (the default for a new account) uses fake money and lets you use test card numbers like 4242 4242 4242 4242. Live mode uses real money and real cards.

Every API key, every product, every webhook endpoint you create exists in exactly one of these two modes. You have separate keys for each. For everything in this guide, stay in test mode until you've deployed to production.

When you switch from test → live, you have to create a Product and webhook endpoint again in live mode. The CLI talks to whichever mode you're authenticated against.

§1Account & API keys

1.1 · Create a Stripe account (or sign in)

  1. Go to dashboard.stripe.com/register. Email + password + business name is enough for test mode. Stripe doesn't require identity verification until you turn on live payouts.
    Privacy note Stripe will email you about activating live mode. You can ignore those emails until you're ready to charge real money.
  2. You'll land on the dashboard in test mode. Look for the test mode toggle in the top-right corner — it should say "Test mode" with a green checkmark. Leave it on.
  3. Bookmark the dashboard home. You'll come back to it.

1.2 · Grab your API keys

From the dashboard, in the left sidebar, click Developers → API keys.

You'll see two keys:

  • Publishable key — starts with pk_test_. Safe to put in client-side code. PocketPlot doesn't actually use this (server-side only), but you'll need it for the front-end Stripe.js if you ever add Elements.
  • Secret key — starts with sk_test_. Treat this like a password. Don't commit it to git. Reveal-click to copy.
💡 Roll keys if you leak one If you accidentally commit a secret key to GitHub, Stripe's GitHub scanner will auto-revoke it within minutes. Roll a new one from the same page — there's a Roll button next to each key.

Copy both into a temporary scratch file. You'll use them in step 4.

§2Create the Product & Price

PocketPlot Pro is a recurring product with a monthly price of $4.99 USD. Stripe's vocabulary is "Product" = the thing you're selling; "Price" = the specific billing configuration under that product. You can have many prices per product (e.g. monthly, yearly, regional variants), but for the MVP you only need one.

  1. From the left sidebar, click Workbench → Products → + Add product.

    You'll see a form like Figure 2. Fill it in:

    • Name: PocketPlot Pro (the customer-facing name)
    • Description: A unique bedtime story in your inbox every night, written just for your child.
    • Image: skip for now (you can add a moon illustration later)
    • Pricing model: Recurring required for subscriptions
    • Amount: $4.99 USD
    • Billing period: Monthly
  2. Click Save product. You'll land on the product detail page.
  3. Find and copy the Price ID. Scroll down to the "Pricing" section. You'll see a card like price_1ABCdef…. That's your STRIPE_PRICE_ID.
Quick reference The IDs you now have:
  • sk_test_... — your secret key
  • pk_test_... — your publishable key (not used by PocketPlot server-side)
  • price_1ABC... — your Pro price id

§3Add a webhook endpoint

Webhooks are how Stripe tells your app that a subscription was created, a payment succeeded, a customer cancelled, etc. PocketPlot listens at POST /webhook/stripe and reacts to five events.

  1. From the left sidebar, click Developers → Webhooks → + Add endpoint.

    You'll see a form like Figure 3.

  2. Endpoint URL: https://your-domain.com/webhook/stripe
    For local dev, use Stripe CLI In step 5 you'll run stripe listen --forward-to localhost:5000/webhook/stripe and the CLI will print a whsec_... URL. Use that for now; replace with your real domain at deploy time.
  3. Events to send: choose Selected events, then check exactly these five: 
    ✓  customer.subscription.created
✓  customer.subscription.updated
✓  customer.subscription.deleted
✓  invoice.paid
✓  invoice.payment_failed

    That's it. Don't select "All events" — you'll get noise (radar, disputes, payouts) you don't need to handle.

  4. Click Add endpoint. You'll land on the endpoint detail page.
  5. Click Reveal under "Signing secret. Copy the value (it starts with whsec_). This is your STRIPE_WEBHOOK_SECRET.
⚠ Rotate the secret when you redeploy Each environment (local, staging, prod) gets its own signing secret. If you delete and re-add the endpoint, you get a new secret. Always update the env var on every deploy.

# bash / zsh
export STRIPE_SECRET_KEY="sk_test_..."
export STRIPE_PRICE_ID="price_..."
export STRIPE_WEBHOOK_SECRET="whsec_..."
export POCKETPLOT_SITE_URL="http://localhost:5000"

You should see this in the logs:

Stripe live mode: secret key configured
Billing: LIVE Stripe
Daily delivery at 20:00 UTC

If you see Billing: MOCK mode instead, one of the env vars didn't get picked up. Check the spelling — they're case-sensitive.

§5Stripe CLI — local end-to-end testing

This is the part that makes the difference between "I think the webhook works" and "I just watched a real Stripe subscription event land in my local server and update the database." The CLI relays events from your Stripe account to localhost:5000 in real time, with real signatures.

5.1 · Install

macOS (Homebrew):

brew install stripe/stripe-cli/stripe

Linux (.deb):

curl -sL -o stripe.deb https://github.com/stripe/stripe-cli/releases/latest/download/stripe_*_linux_amd64.deb
sudo dpkg -i stripe.deb

Windows: download the MSI from the releases page.

Verify with stripe --version (should print something like stripe version 1.50.3).

5.2 · Login

stripe login

This opens your browser to a Stripe page asking to pair the CLI with your account. Click Allow access. The CLI will print Done! The Stripe CLI is configured for <your account>.

Headless / no browser If you're on a remote server, run with stripe login --interactive and copy the URL it prints into a browser on your laptop. Or set the STRIPE_API_KEY env var to your secret key directly (less safe; skip if you can).

5.3 · Forward events to your local server

Open a second terminal and run:

stripe listen --forward-to localhost:5000/webhook/stripe

You'll see something like:

> Ready! Your webhook signing secret is whsec_1234567890abcdef...
> 2026-08-21 19:50:00  --> customer.subscription.created [evt_1ABC]
> 2026-08-21 19:50:00  <-- 200 [evt_1ABC]

Two things to notice:

  1. The signing secret the CLI prints is for this CLI session only. Use it as your STRIPE_WEBHOOK_SECRET in your local dev shell so the signature verification in PocketPlot passes.
  2. The --> and <-- lines show the request and response in real time. If your app returns a non-2xx, the CLI retries with exponential backoff — the same behavior production gets.

Keep this terminal open. It's your window into the live event stream.

5.4 · Trigger test events

You have two ways to fire events at your local server:

Option A — synthesize events with stripe trigger

No need to actually create a subscription in your dashboard. The CLI ships with canned events:

stripe trigger customer.subscription.created
stripe trigger customer.subscription.updated
stripe trigger customer.subscription.deleted
stripe trigger invoice.paid
stripe trigger invoice.payment_failed

Each one fires a real event with a real signature at your listening endpoint. In your CLI terminal you'll see the request and response, and in your PocketPlot log you'll see Stripe customer.subscription.created for sub#X (active).

Option B — drive it through the UI

Open localhost:5000 in your browser. Sign up, sign in via the magic link, click Upgrade to Pro. With live mode enabled, this opens a real Stripe Checkout. Use test card 4242 4242 4242 4242, any future expiry, any CVC, any postal code. On success you bounce back to /me as Pro. Watch the CLI terminal — you'll see the customer.subscription.created and invoice.paid events arrive in real time.

5.5 · Verify in the app

After triggering customer.subscription.created, check the database:

sqlite3 pocketplot.db "SELECT email, plan, subscription_id, subscription_status FROM subscribers;"

You should see plan=pro on the row you just triggered for.

Then trigger customer.subscription.updated (with cancel_at_period_end=true in the event body if you want to test the graceful cancel) and confirm the status field updates.

Finally trigger customer.subscription.deleted and confirm the plan downgrades back to free.

§6Troubleshooting

"Webhook signature verification failed"

Your STRIPE_WEBHOOK_SECRET doesn't match the secret Stripe signed with. In dev, this usually means you copied the dashboard's secret instead of the one stripe listen printed. In prod, it means the secret rotated. Get the new one and restart the app.

"Webhook for unknown subscriber" warning in the log

The webhook arrived for a customer/subscription that isn't in your database. Either the user signed up with a different Stripe account, or this is a leftover event from a previous test. Safe to ignore unless production.

Events arrive but DB doesn't update

Open the CLI terminal — if the response is 200 but no DB change, the event is reaching your app but the lookup is failing. Add a log.info(...) in apply_stripe_event_to_subscriber to trace.

Live card 4000 0000 0000 0002 is declined

That's the correct behavior — that test card simulates a generic decline. Use 4242 4242 4242 4242 instead. Stripe's test card reference has the full list.

I keep getting redirected to login after upgrading

The session cookie didn't survive the Stripe redirect. Check that POCKETPLOT_SITE_URL is set to the same domain the user is browsing on (not localhost if they're using a real domain, or vice-versa). Flask sessions are domain-bound.

CLI says "no such command trigger"

You have an old CLI (<1.50). Update.
